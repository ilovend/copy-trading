# 登录态更新（cURL）

适用版本：v2.0.33 及以后。

## 结论

登录态只需要一份有效的 Binance 网页登录 Cookie。推荐从下面任意一条私有请求复制 cURL：

```text
/bapi/futures/v1/private/future/copy-trade/account/get-user-ct-balance
```

```text
/bapi/futures/v1/private/future/copy-trade/copy-portfolio/detail-list
```

URL 必须同时包含：

```text
/bapi/
/private/
/copy-trade/
```

## 不接受的请求

以下请求会被驾驶舱拒绝：

```text
authcenter/auth
/bapi/fe/messagecenter/...
/bapi/asset/...（钱包/资产）
页面 HTML
JS / CSS 文件
```

`bnc-challenge-token` **不是每次登录都会下发**，缺失时不需要处理，也不是登录态失效的判断依据。

## 操作步骤

1. 浏览器登录 Binance，完成“信任设备”验证。
2. 打开复制交易页面。
3. 按 F12 → Network。
4. 过滤：

```text
get-user-ct-balance
```

如果看不到，再过滤：

```text
copy-portfolio
```

5. 选择一条状态 `200` 的私有请求。
6. 右键 → Copy → **Copy as cURL (bash)** 或 **Copy as cURL (cmd)**。
7. 打开驾驶舱 → 账户配置 → 用 cURL 更新登录态。
8. 粘贴 → 解析、校验并写入 `session.json`。

## 校验结果

成功时会显示类似：

```text
登录态已更新：有效，N 个跟单组合
```

后台会用 `copy-portfolio/detail-list` 再校验一次 Cookie。

如果返回 401：

```text
登录状态已经失效，请重新登录
```

说明 Cookie 本身已过期，不是 URL 格式问题，需要重新登录后再复制。

## 有效期与自动恢复

- Binance 网页登录态不是固定 5 天；5 天通常是“信任设备/免验证”窗口，不等于 Cookie 一定保活 5 天。
- 复制进程每 5 分钟 keepalive listenKey。
- v2.0.31 起会捕获 `Set-Cookie` 并写回 `session.json`。
- 401 时进程不退出，等待新的 cURL 自动 reload。
- 不要把同一份 Cookie 同时给浏览器和路由器长期使用；浏览器重新登录/刷新可能让旧副本失效。

## `.env` 与 session 的优先级

当前优先级：

```text
.env 的 BINANCE_COOKIE + BINANCE_CSRFTOKEN
高于
session.json
```

不要在两处同时维护旧 Cookie。推荐 `.env` 留空，只通过 cURL 写 `session.json`；否则 `.env` 的旧值会覆盖新 session。

## 5 天信任

“信任此设备 5 天”是 Binance 服务端/设备层状态，可能还涉及 localStorage、设备指纹、IP、UA。只复制 Cookie/headers 无法保证一定获得 5 天寿命。

如果重新登录、从正确的 `get-user-ct-balance` 请求复制后仍然很快 401：

1. 使用独立浏览器 profile；
2. 不要在复制后继续在该浏览器操作同一账号；
3. 不要在另一台设备重新登录；
4. 必要时用 Playwright 持久化浏览器 profile，定期同步 Cookie 和 localStorage。

## 安全

`session.json` 等同于账号网页登录态，能查看/操作跟单账户。不要提交、截图或发给他人；更新后权限应为 `0600`。
